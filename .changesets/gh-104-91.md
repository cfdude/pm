# gh#104 + gh#91 — commit-nudge OBSERVES the repository instead of parsing the command string

### Fixed

- **A command that merely *mentions* `git commit` no longer nudges (#104).** The `PostToolUse`
  hook decided a commit had happened by testing the Bash command's TEXT against
  `/git\s+commit/`, so an `rg` for the phrase, a heredoc writing commit-convention docs, or an
  `echo` produced an advisory asserting a commit that never happened — repeated noise arguing for
  bookkeeping in response to an event that did not occur. It now watches HEAD: a small
  git-ignored watermark (`.conductor/commit-watch.json`) records where HEAD was on **every**
  Bash call, and the hook speaks only when HEAD has moved AND `git reflog` says the move was a
  commit (`commit:`, `commit (initial):`, `commit (amend):` — a `checkout`, `reset`, `merge`,
  `rebase` or `pull` moves a pointer at objects that already existed and is silent).
- **No AUTO-DETOUR is logged when there is no active epic (#91).** A detour is by definition an
  interruption of an active epic; with none there was nothing to detour FROM, and the entry
  carried an empty epic field (`AUTO-DETOUR\t-\t…`) describing an interruption that never
  happened — then asked the human to hand-clean `detours.log`, the exact hand-editing pm exists
  to remove. Observed twice in one session against `/pm:upgrade`'s own
  `chore(pm): upgrade conductor to <ver>` commit. The sibling `DETOUR-COMMIT` branch needed no
  change: it is already gated on a live detour frame, which is strictly stronger.
- **Every commit FORM is now noticed, because none of them is parsed.** `git commit -am`,
  `-F file`, a heredoc, an editor commit with no message flag at all, and a message carrying an
  escaped quote were each invisible to the `-m "([^"]*)"` capture. The first four produced an
  empty subject that short-circuited the landed-check — so a REJECTED `-am` commit still wrote a
  false `DETOUR-COMMIT` line, gh#65's original symptom surviving in a flag form — and the last
  truncated at the first `\"`, which HEAD then CONTRADICTED, silently suppressing a commit that
  genuinely landed. On the observed path the subject now comes from the commit itself, so this
  closes as a class rather than one flag at a time, including flags git has not invented yet.

### Changed

- **A commit that lands during a call whose text never says `git commit` is now noticed** — a
  wrapper script, a `make` target. That is a false NEGATIVE the text check used to have.
- **A backgrounded commit is caught on the next tool call rather than lost.** The hook fires
  while `git commit` is still running, so HEAD has not moved and nothing is asserted; the
  watermark is then stale by exactly one commit and the very next Bash call notices it. Under
  the text check (gh#68) that commit was dropped permanently.
- **A commit made outside the agent's own Bash calls** — the user's terminal between sessions,
  another worktree on the same HEAD — is now attributed to whichever Bash call fires next. This
  is a deliberate new false-positive class, accepted because the assertion it makes ("a commit
  landed") stays TRUE; only its association with that particular command is arbitrary. Noticing
  a commit is not purely advisory, though — it also runs the archived-epic self-heal and
  `render()`, so such a commit can re-render the tracked `PROJECT.md` from an unrelated Bash
  call. Render-on-commit is established behaviour here (see CONTRIBUTING), so this widens an
  existing property rather than introducing one.

### Degradation

- The hook runs on every Bash tool call in every pm-initialized project, so it degrades to doing
  nothing rather than erroring. When nothing can be observed — no git, not a repository, reflogs
  disabled (`core.logAllRefUpdates=false`), a watermark that is missing, unreadable or corrupt —
  it falls back to the exact pre-observation text heuristic, which is also what keeps
  commit-nudge's archived-epic self-heal running in a repo with no git at all. Every read and
  write in the new module is individually caught; a read-only checkout that cannot write the
  watermark simply stays on the fallback rung forever, which is the old behaviour.
- The cold-start rung (the first hook run in a repo, before any watermark exists) still parses,
  so both flag-form defects above are fixed THERE too rather than only routed around: the
  capture now recognises bundled short-flag clusters (`-am`, `-qm`) and is backslash-aware, with
  shell escaping undone before the comparison.

### Cost

- One `git rev-parse` per Bash tool call. `git reflog` is spawned only when HEAD actually moved
  against a known baseline, and the watermark is written only when its value changes.

### Known, and deliberate

- **The ignore line arrives with `/pm:upgrade`, not with the plugin.** `.conductor/commit-watch.json`
  is added to `ensureGitignore()`, which `init()` and `upgrade()` both run — no `MIGRATIONS`
  entry, because nothing in `state.json` is transformed. Exactly the route
  `.conductor/write-conflicts.latch` took for the same reason. So a repo that updates the plugin
  and has not yet run `/pm:upgrade` grows one untracked file until it does, which the documented
  update sequence (plugin → `/reload-plugins` → `/pm:upgrade` per repo) closes.
- **Two concurrent Bash calls can both notice the same commit** — one backgrounded, one in the
  foreground — and write a duplicate `DETOUR-COMMIT` line. Duplication, never a lost entry, is
  the safe direction; a torn read of the watermark yields no baseline, which is the fallback
  rung, not a denial.
