# gh-149 / gh-148 — one rule for a missing flag value, and the epics a design document already names

## Fixed — #149: a flag accepted on one surface and refused on the other

`update-epic --plan` with no value was refused; `add-epic --plan` with no value was **silently
dropped** — exit 0, epic created, field absent. Same flag, same registry row, two behaviours,
because each command carried its own hand-written list of the flags it happened to check.

**Decision: refuse on both — on every surface.** Accepting on both is the only reading that
*removes* a working catch, and the mistake it catches is silent and unrecoverable (a shell that
ate the value; a trailing flag with nothing after it). The rule now lives on the shared
`EPIC_FLAGS` declaration rather than in each command:

- a row marked `valueless: true` (`--clear-links`, `--no-deferrals`, `--done`) is exempt;
- **every other row is value-bearing** and its flag is refused when the value is missing or blank;
- a row may carry a `requires` phrase, so a bespoke refusal one command grew — `--link` pointing
  at `--clear-links`, `--wont-do` demanding a reason — now reaches *every* command that accepts
  the flag instead of being a second behaviour on a second surface.

Applied at all **six** write surfaces the registry names, not the two the issue reports:
`add-epic`, `update-epic`, `record-gate-review`, `record-cross-spec-review`, `release`, and
`add-many` (whose flag surface is its batch document's keys — a key present with a non-string or
blank value is refused in the validation pass, so a batch with one offender creates none of its
entries). `record-gate-review` checked no flag for a value at all: a valueless `--reviewer`
recorded a gate verdict with the reviewer identity simply absent.

### Behaviour change — what breaks, and for whom

Six spellings that used to exit 0 now exit non-zero. Every one of them wrote nothing, or wrote
something unusable, so what breaks is a no-op that looked like a success:

| Was | Now |
|---|---|
| `add-epic --plan` (and `--link`, `--title`, `--priority`, …) with no value | refused |
| `record-gate-review … --reviewer` with no value | refused |
| `release … --target` / `--member` with no value | refused |
| `record-cross-spec-review … --reviewer` with no value | refused |
| any of the above with a **blank** value (`--plan "   "`) | refused |
| `add-epic --title ""` → fell back to the id | refused |
| `add-many` batch key with `true` / `7` / `""` → dropped | refused |

A mechanical sweep (`rg` over `commands/`, `skills/`, `hooks/`, `agents/`, `scripts/`, `docs/`,
and the rules block `rules.mjs` emits) found **no caller anywhere in this repository or in the
emitted instructions that passes a value-bearing flag with no value.** The only breakage is a
user script that was relying on exit 0 from an invocation that already wrote nothing.

No migration: no state shape changed. The rule is a parse-time refusal.

## Added — #148: `verify-specs --headers`

Design documents already declare their epics in a header. Deriving the association from filenames
placed 8 of this repository's 10 documents and **structurally could not place the other two** —
`tracker-direction-and-freshness-design.md` covers three epics whose ids share no stem with the
filename, which is precisely the many-to-one case `specPath` exists for.

`verify-specs --headers` reports, for every **uncovered** document, the epic ids its header names
and the `update-epic <id> --spec <path>` line that would attach each one. It **proposes and never
applies** — the same split `triage` uses for asks: mechanical candidate set, agent's verdict. A
header id that names **no epic in the record** is reported as a finding rather than inventory,
from covered documents too.

**The parse is label-agnostic and region-bounded**: any `**Anything:**` line in the leading
metadata block opens it, the first blank line ends it, and backtick-quoted tokens matching the
epic-id format are the candidates, each carrying the author's own label verbatim. Two rules were
run against this repository's ten real design documents before choosing; an allowlist of label
names dropped three genuine ids filed under `**Depends on (all three must land first):**`. The
chosen rule recovered 26 of 26 with zero false candidates.

It is its own arm rather than always-on output because it reads a document's **body**, which the
bare coverage report deliberately does not. The bare report now points at it.
