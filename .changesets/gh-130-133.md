# gh-130 + gh-133 — the disposition write path

Both are defects in the same write path: the one that records how an epic ended.

### Fixed

- **#130 — a mistyped disposition had no correction verb.** An agent-recorded disposition was
  unreplaceable, so recording `delivered` where `superseded` was meant (or attaching the wrong
  reason) left hand-editing `.conductor/state.json` as the only route — on the *terminal* record
  of what happened to a piece of work. `update-epic <id> --status archived --outcome <o>
  --correct-disposition "<why the recorded one was wrong>"` now corrects it. The ordinary verb
  still refuses, and its refusal now names the correction route instead of being a dead end.

  A correction is **deliberate** (never reachable by re-running the ordinary verb; refused when
  there is no agent-recorded disposition to correct), **self-describing** (the flag's value is the
  justification and is kept on the record as `disposition.correction`), and **non-destructive**
  (the prior record survives verbatim under `disposition.superseded`, one level deep, exactly as
  `record-gate-review` caps its own nest). PROJECT.md and the brief render
  `· corrected (was <prior outcome>)` beside the new outcome, so a correction is distinguishable
  from an original by anyone reading afterwards. The superseded record's `carriedTo` joins the
  dangling-epic-reference sweep like every other holder of an epic id.

- **#133 — recording an honest disposition on a backfilled epic reverted its archived task
  counts.** `isArchiveBackfilled()` asked the DISPOSITION record who registered the epic
  (`recordedBy: "archive-backfill"`), but the interactive verb replaces the disposition wholesale
  with an agent's own, which carries no `recordedBy` by design. Registration provenance therefore
  lived inside the one field whose entire contract is that an agent overwrites it — so a change
  registered at `2/3` rendered `—` the moment somebody recorded the truth about it. Registration
  provenance now lives on the EPIC as `registeredBy`, orthogonal to the disposition and untouched
  by any disposition write.

### Migration

**A `MIGRATIONS` entry keyed to `0.32.0`** (`lift archive-backfill registration provenance from
the disposition onto the epic`) — existing data must be TRANSFORMED, not merely extended: every
repo written before this carries the provenance only on the disposition, and the reader now asks
the epic. Additive, idempotent, `state`-only, scoped to the backfill's own token.

**The entry's `release` must EQUAL the version this ships in — re-key it if the release number
moves.** `upgrade()` applies an entry when `cmpVer(entry.release, state.pmVersion) > 0`, and
`stampVersion` stamps `pmVersion` to the running plugin version. So if this shipped in 0.33.0
with the entry still keyed `0.32.0`, any repo that ran `/pm:upgrade` while the plugin was at
0.32.0 is stamped `0.32.0`, `cmpVer("0.32.0", "0.32.0") === 0`, and **the lift never runs for
exactly those repos** — their backfilled epics render `—` and enter the completion-shaped checks
permanently, with nothing in `state` left to recover the fact from. "0.32.0 or later" is the one
reading that breaks it. (Until `plugin.json` reaches the keyed version the entry replays on each
`/pm:upgrade`; it is guarded on an absent `registeredBy`, so a replay is a no-op.)

The migration cannot recover an epic whose backfill stamp was ALREADY overwritten before it ran:
nothing in `state` still holds that fact. Such an epic keeps rendering `—`, exactly as it does
today. That is the bug's residue, not a new one.

Repos that update the plugin but have not yet run `/pm:upgrade` will, in the interval, see
backfilled epics render `—` for progress and appear in `integrity`'s completion-shaped checks —
the ordinary pre-migration window, cleared by `/pm:upgrade`.

### Docs

`commands/epic.md` documents `--correct-disposition`, what makes a correction legitimate, and the
extension of the dangling-reference sweep. **README.md and the Mintlify site still owe the same
update** — `--correct-disposition` is a new user-facing flag.
