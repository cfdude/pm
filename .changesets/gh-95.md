# gh#95 — stories: atomic creation, and a terminal disposition for work that will not be done

### Added

- **`--add-story` is repeatable and works on `add-epic` and `add-many`, not just `update-epic`.**
  An epic's milestones now land in the SAME write as the epic:
  `add-epic --id deploy-pipeline --lane superpowers --add-story "Build" --add-story "Cut over"`.
  An `add-many` batch entry carries a `stories` array of plain titles or `{"title", "done"}`
  objects, validated in the same up-front pass as everything else — a blank title refuses the
  whole batch and creates nothing. Measured cause of the gap: with stories addable only one
  `update-epic` call at a time after registration, 91.7% of epics in a 108-epic audit had none.
- **`update-epic <id> --story <n> --wont-do "<reason>"`** — a story's terminal disposition. A
  `done` boolean holds two states and the record needs three: open, completed, and deliberately
  not being done. Deletion is never the third state, so the row and its title always survive and
  only the terminal state differs. The reason is required; a recorded disposition is never
  silently replaced; a `done` story cannot be dropped and a disposed one cannot be ticked.

### Changed

- A disposed story leaves **both** sides of the progress ratio, exactly as a
  `<!-- pm:lifecycle -->` task does: `3/3 stories · 2 disposed`, never `5/5` (which would claim
  completion for work nobody did) and never `3/5` (which would leave the archive gate refusing
  forever with no honest key).
- **The archive refusal now names the outstanding stories, and offers `--wont-do` instead of a
  remedy that could not be performed.** No new refusal was added — the handoff demand already
  refused `--outcome delivered` while `outstandingWork() > 0`, and inline stories are the first
  progress source that reads. The defect was the message: it directed the caller to put
  `<!-- pm:lifecycle -->` on the task's own line, which an inline story does not have, leaving
  only `--carried-to` — naming a receiving epic for work that was dropped rather than moved,
  which is the fabricated record the same message warns against. The checkbox path's message is
  unchanged, because there the marker IS performable.

### Not built, deliberately

- **Stories are still optional.** Making them mandatory has no measured support and the audited
  record says the field's meaning is still migrating: 0 of 148 epics in this repo use the
  `description`/`notes` carriers that 0.27.0 shipped, and ~80% of the live stories on open epics
  are findings and rationale rather than milestones.
- **No story-level `--moved <epicId>`.** The audited record holds zero story-level moves, the
  epic-level `--carried-to` handoff already names a receiving epic, and a story-level receiver id
  would be a new cross-record pointer needing its own deletion-path sweep.

### Migration

**None.** `stories[n].disposition` is an added optional field; a story written by any prior
version loads unchanged and still counts as outstanding, which is what it always meant.
