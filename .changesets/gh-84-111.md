# gh-84 / gh-111 — advisory claims, and an activity log that ships with its reader

## Added — `claim` / `unclaim` / `owners` (#84)

Advisory ownership markers for multi-session and multi-repo work. An orchestrator dispatching
epics into a sibling repo's conductor can now ask *who is doing this, since when, and is it safe
to write here* — questions `state.json` could answer none of.

```
claim   <epic-id> --session <name> [--ttl <minutes>] [--steal]
claim   --repo    --session <name> [--ttl <minutes>] [--steal]
unclaim <epic-id> --session <name> [--steal]
owners  [--json]
```

`--session` is required; `PM_SESSION` supplies it and an explicit flag outranks the environment.

**Advisory means one surface refuses, and only one.** `claim` and `unclaim` refuse over another
session's LIVE claim, exit non-zero, and write nothing — so "two sessions both claim" has no
silent-corruption reading, because the loser performs no write at all. Every other verb behaves
against a claimed epic exactly as before. The real write race stays with `state.json`'s revision
guard (#83), which `--steal` deliberately does not touch.

**Three deviations from the issue's suggested shape, each argued rather than assumed:**

1. **`unclaim`, not `release`.** `release` is already this engine's version-release verb.
2. **A stated TTL, not `heartbeatAt`.** A heartbeat nothing beats is `claimedAt` in a costume, and
   it makes the staleness threshold wrong in both directions — a live session reads stale after N
   quiet minutes, a crashed one reads live for N minutes past its last write. The only true
   auto-bump chokepoint is `saveState()`, which does not know which epic is being written. The TTL
   is recorded ON the claim (default 120 min for an epic, 30 for the repo marker), so a claim
   taken under one default keeps its meaning when the default changes. Re-claiming extends it.
3. **The repo marker is a sidecar**, `.conductor/session-claim.json`, not a field in `state.json`.
   It answers *is it safe to write to `state.json`*; putting it inside the file it is worried
   about — where setting and clearing it bump `revision` and can themselves conflict — inverts
   its purpose. Same argument `write-conflicts.mjs` opens with.

**What expires a claim:** its own TTL, read rather than swept, which is what lets `owners` and
`integrity` agree without either of them writing. **What reports a stale one:** `owners` when
asked, and `integrity`'s new `advisory-claim-shape` check when nobody thinks to ask — which
matters, because a stale claim is by construction left by a session no longer there to ask.
Archiving an epic clears its claim and says so; an archived epic cannot be claimed.

`owners` is declared and **behaviourally verified** read-only, so pointing it at a repo you do not
own does not dirty it (#85's rule, applied to the verb that asks #85's question).

A shared `resolveSession()` (`lib/session-identity.mjs`) is the single answer to "who is acting",
for both this and the activity log below — the field family the maintainer's design work links.

**No `MIGRATIONS` entry:** `epic.claim` is an added optional field, not a transform of existing
data. The `.gitignore` back-fill rides `ensureGitignore()`, which `upgrade()` already re-runs
(#106's rule).

## Added — `set-activity-log` / `activity` / `purge-logs` (#111)

An optional, **off-by-default** append-only record of conductor state transitions, and — in the
same change, because that was the stated condition — the reader that answers for it.

**The reader ships with the writer.** A log nothing reads is a data graveyard: write-path
complexity, rotation, retention and a purge CLI all paid immediately, for a benefit that stays
speculative until something consumes it. So every section `activity` prints answers a question the
issue asks by name, and nothing is recorded "in case it is useful later".

| Question the issue asks | Section |
|---|---|
| How long did an epic sit `queued` before it was picked up? | TIME TO PICKUP |
| How many detours interrupted it? | DETOURS |
| Which lane was chosen, and did the work prove it wrong? | LANES (registrations + re-routes) |
| When was a gate verdict recorded? | GATES |
| How often does an agent take the instructed path vs. work around it? | **OUT-OF-BAND WRITES** |

**Out-of-band writes are why it earns its overhead.** Every event carries the `state.json` revision
**range** it covers (`fromRevision`, `revision`), so a revision the file reached that no event
accounts for is a write the *engine* did not make — a hand-edit. That is #110 (a gate defeated
silently, discoverable only by `jq` across 15 repos) turned into a query. The range rather than a
single number is load-bearing: `update-epic` saves twice (`saveState`, then `render`), and a
single-number event would report every ordinary write as a hand-edit — the flagship section would
have been pure noise.

**One chokepoint, not an instrumentation sweep.** Events are derived by diffing `state.json` across
one invocation, from a single point in the engine's dispatch, never emitted by hand from each of
the ~25 verbs that write state. A list of emit sites typed from memory goes stale the moment a verb
is added, and a verb that forgot to emit would be invisible in exactly the log built to find
invisible things. Registered on `process.on("exit")` rather than in a `finally`, because
`rg -n "process\.exit" scripts/lib/` finds one mutating verb that writes state and then exits —
and `process.exit()` skips `finally` while running exit handlers.

**Rotation, retention and purge ship with it, sized rather than guessed** (the maintainer's ruling):
128 KB segments (≈680 events ≈ 37k tokens — a segment must be fully readable in one pass by an
agent), named `activity-<ISO start>.log` so retention and `--since` are answerable from the
filename without opening a file, and 1 GB total per project, oldest first, pruned at the rotation
boundary only so the read never lands on the write path. Retention never deletes the last remaining
segment.

`purge-logs [--kind activity|conflicts|detours|all] [--keep <n>] [--over <size>]
[--older-than <days>] [--dry-run] [--yes]` refuses to guess twice: with no selector it removes
nothing, and without `--yes` it prints the plan and removes nothing. That second refusal is the
non-interactive form of "requires confirmation" — this engine is driven by agents and hooks, so a
prompt on stdin would hang rather than confirm.

`.conductor/activity/` is git-ignored by `init` **and** by `upgrade` (#106's rule). Off is the
default and stays it; `state.activityLog` is an added optional field, so **no `MIGRATIONS` entry** —
a state file written by the previous version loads unchanged and resolves to off, which is the same
answer its absence already gives. Nothing is recorded retroactively, and the reader says so rather
than reporting a bare zero.
